Ticket 5: make the learning run complete, inspectable and recoverable

1. What are we trying to learn?

The larger research question is: what does fine-tuning write into a model, and how does the training objective affect that write? Pilot 2 produced the SFT arm: the model learned to imitate gold GSM8K solutions. Pilot 3 measured its internal activation changes on fixed tokens. Pilot 4 adds the GRPO arm: the model generates solutions, receives answer-correctness rewards, and learns from differences among its own answers.

Ticket 5 produces the GRPO adapters. It does not yet establish whether performance was preserved or what those adapters wrote internally. Those are the next tickets.

2. What comes in, and what comes out?

Inputs from earlier ticketsFrozen protocol and review; exact 512 training IDs/order; pinned model/tokenizer; FP32 rank-1 configuration; optimizer settings; final cap/filter/batch settings; monitor actions; validated GRPO loss.
Outputs of Ticket 5Adapters at 0/8/16/32/64; optimizer/scheduler/RNG state; 4,096 accepted training draws; 64 step logs; attempt/failure evidence; hashes and completion markers.

The new run must start from a fresh untuned model and zero-initialized adapter. Preflight’s updated adapters are disposable. Otherwise we would accidentally train for extra unrecorded steps before step 1.

512 distinct problems ÷ 8 problems/update = 64 optimizer updates
64 updates × 8 problems × 8 answers = 4,096 accepted training completions

A “completion” is a sampled answer, also called a rollout. Two draws can have identical text and still be distinct draws. IDs record which problem, update and draw each belongs to.

3. One optimizer update, from first principles

A neural network assigns probabilities to possible next tokens. Training changes weights so selected token sequences become more or less likely. GRPO first needs a reason to prefer one generated answer over another.

Take 8 problemsNext IDs in the frozen order
→
Generate 64 answers8 sampled answers/problem; current adapter; temperature 1
→
Score each answerFlexible v3 → binary reward; strict score recorded separately
Compare within groupsTurn rewards into advantages, one problem at a time
→
Loss → backwardCompute probabilities of saved tokens and adapter gradients
→
Clip → AdamW stepOne update after the complete 64-answer window

A concrete reward example

Suppose the eight answers to one problem have rewards [1,1,1,1,0,0,0,0]. Their mean is 0.5. A correct answer is above this group’s average; an incorrect one is below it. The existing implementation uses:

advantage = (reward − group mean) / (sample standard deviation + 0.0001)

For this example the advantages are approximately +0.935 for each correct draw and −0.935 for each incorrect draw. Positive advantages encourage the corresponding sampled tokens; negative advantages discourage them. The standardization makes the signal depend on performance relative to answers to that same problem.

If all eight rewards are identical, advantages are zero: a dead group supplies no ranking signal. It might be an easy problem with all correct answers or a hard one with all incorrect answers. Zero current gradient does not necessarily mean zero weight movement: Adam can retain momentum from earlier updates.

Why generate, then run another forward pass?

Generation chooses tokens without keeping a training computation graph. The training forward pass reads those saved tokens, calculates their log probabilities, and retains the graph needed for backpropagation—the calculation of how each LoRA parameter affects the loss. This is not a second set of answers.

The existing pinned TRL loss uses DAPO normalization over all completion tokens in the complete window. The policy is updated once per fresh window; β = 0 means no KL penalty is added. A separate frozen reference model is therefore not required for this training loss. Later Ticket 8 measures KL as a diagnostic.

Scoring affects learning here. In Pilot 1 a parser error altered a reported score. In Ticket 5 it can also send the wrong training signal. Invalid and capped responses receive reward 0; strict correctness is recorded independently. A strict-correct completed answer must also be flexible-correct. A capped answer may be correctly extracted yet still receive zero optimization reward under the explicit cap policy.

4. What batching does—and does not—change

The algorithmic batch stays at eight problems and 64 answers per update. Memory batching determines how many of those answers fit on the GPU at once.

Generation groups = 2Generate 2 problems × 8 draws = 16 answers together. Repeat four times to collect the 64-answer window.
Backward groups = 1Process 1 problem × 8 answers at a time. Accumulate eight gradient contributions, then perform one optimizer update.

These numbers illustrate grouping; the actual values come from Ticket 4’s frozen preflight. The examples in one memory batch run together on one GPU. Optimizer updates remain sequential because update 2 must sample from the model produced by update 1.

The loss denominator must stay tied to the whole window. Dividing each memory chunk independently or dividing accumulated gradients a second time can change the effective training strength. Ticket 3 already tested this arithmetic; Ticket 5 must preserve it while adding the full loop.

Gradient checkpointing is different from saved training checkpoints: it discards some temporary activations during a backward pass and recomputes them to save GPU memory. It does not save progress to Drive.

5. Why saving only the adapter is insufficient

The adapter weights tell us what the model is now. They do not tell us how to make the next update identical after a restart.

Saved objectWhat it carriesWhy it matters
LoRA A/B weightsThe learned rank-1 changes in 196 projectionsRestores the policy and supports later evaluation. The frozen base model is loaded from its pinned revision.
Optimizer stateAdam moments and update countSame weights with fresh Adam state can produce different next updates.
Scheduler stateLearning-rate schedule positionMaintains the declared execution state, even with a constant schedule.
RNG statePython, NumPy, Torch CPU/CUDA random-generator stateRestores the stochastic continuation rather than restarting randomness from the beginning.
Trainer/data-order stateGlobal step, ordered problem IDs and next cursorAvoids skipping/repeating problems or loading a different accumulation position.
Previous pre-clip gradientFlattened vector with fixed parameter-name orderMakes gradient cosine across the restart meaningful; step 33 compares with step 32, not a missing vector.
Accepted-history manifestWhich rollout/log records belong to this checkpoint, plus file hashesConnects the weights to their exact scientific training history.

A sealed checkpoint is a saved collection whose required files and hashes have passed verification, with its completion marker published last. A half-written adapter directory is not a valid recovery point.

Step diagnostics: what should I actually read?

DiagnosticQuestion it answers
Reward / strict score / cap fractionAre training answers improving, changing format, or being censored?
Dead-group fractionHow much of this window supplies a relative learning signal?
Mean and p90 lengthIs output length changing, including the long-answer tail?
Loss / learning rateWhat optimization calculation was performed? Loss alone is not held-out accuracy.
Pre-clip gradient normHow large was the gradient before the norm-1 clipping rule?
Consecutive gradient cosineAre consecutive updates being pushed in similar or opposing parameter directions?
Adapter norm / movementHow much are adapter parameters changing? This is not yet an activation write or behavioural effect.

Gradient cosine is undefined at the first step or when either gradient is zero. “Undefined” must remain an explicit reason, rather than becoming a misleading zero cosine.

6. Recovery: weights and history restart together

Checkpoint 32 sealedAccepted history: updates 1–32
→
Updates 33–45 attemptedThen interruption; no checkpoint 64
→
Restart from 32Restore all state; preserve old attempt as diagnostics
→
Redo 33 onwardNew accepted continuation; no double counting

The interrupted answers may remain on disk for diagnosis, but they are excluded from the final scientific record. Recovery does not continue from “the last line in responses.jsonl.” The last sealed checkpoint is the only authoritative boundary.

The checkpoints are 0, 8, 16, 32 and 64. A failure near step 64 can require repeating almost the whole 32-step final interval. This is a deliberate simplification: it avoids the complexity of exact mid-window recovery, while retaining complete checkpoint-state recovery.

Why all these identity checks? If the restart silently changes the scorer, prompt order, cap, model revision or runtime, it is no longer the same execution. Rejecting incompatible reuse protects the meaning of the comparison. A hash detects changed contents; it does not prove scientific correctness.

Why process checks? Earlier notebooks continued printing “running” after their child process had died. Ticket 5’s progress must check actual exit state and saved evidence. A PID or a stale status file cannot establish success.

Example live counters at update 16:
optimizer updates = 16 / 64
distinct training prompts = 128 / 512
draws produced in this continuation = 1,024
latest sealed checkpoint = 16
accepted history = 1,024 draws

Between checkpoint boundaries, completed update counters and the sealed recovery position differ. Both should be visible. A success marker requires all 64 updates, all 512 IDs, all 4,096 accepted draws and final integrity checks.

These are proposed implementation responsibilities. Exact new filenames and helper signatures are not frozen scientific decisions. They must preserve the approved experiment and existing test seam. Any new scientific choice still needs explicit resolution.

The existing red/green process means each new behaviour is first tested in a way that fails before implementation. The goal is evidence that the required behaviour works—not a large number of tests that simply mirror helper code.

9. What success means at this ticket

Engineering success: a verified 64-step training history and five reproducible adapters, with correct recovery and no silent settings changes.

Scientific outcome: still unknown here. Training reward can rise while held-out accuracy falls; shorter outputs alone do not establish capability loss. Ticket 6 tests behaviour on the same held-out problems. Ticket 7 measures internal writes on fixed tokens. Ticket 9 combines those findings with the existing SFT arm and documents remaining confounds.

We are building the record that makes those later interpretations possible. The record itself is not a claim that GRPO works better, is safer, or writes more economically.
