# Review of round-4 implementation fixes

Reviewed commits `3cf8537..f5add6e` inclusive (diff from their parent `ad64fcc`), including `review-response-round-4.md`. The response is substantially implemented, but the following material gaps remain. These are review-time observations; no GPU, Colab, Pod, or paid-resource run was performed.

1. **blocking — a stage cap can still be bypassed on retry.** `Chain.run` records a stage as completed and saves the state before checking whether it exceeded its cap at completion (`pilot_eval/attribution_chain.py:521-540`). On retry, completed stages are skipped before any per-stage cap check (`:489-492`). A CPU harness reproduced a preflight taking 200 s with a 50 s cap: attempt 1 stopped before production, but attempt 2 skipped preflight and completed all stages with 200 s still charged to preflight. Enforce the persisted per-stage cap before resuming or starting work, and do not persist an over-cap stage as eligible to bypass the stop. Also test a cap reached at an interrupted unit boundary, not only at stage completion.

2. **blocking — recovery can report a complete run and backup while completed-stage artifacts are missing.** Completed-stage state is on the volume, but expected units/runs are in-memory (`attribution_chain.py:384-396`), are not reconstructed for skipped stages (`:489-492`), and `restore_from_volume` only restores artifacts the volume happens to contain (`:292-320`). In a CPU fixture using the real snapshot/restore with FakeHub, a completed freeze was present in the first HF backup but a simulated volume-copy failure left it off the volume. After deleting local work, a retry skipped all completed stages and produced an HF snapshot labelled `complete` with `missing_work=[]`; a clean restore lacked the freeze. Persist and reconcile the expected artifact set across attempts, verify every completed stage's required artifacts, and restore from a verified backup or refuse/rerun when they are missing. A hash of artifacts that happen to be present does not establish completeness.

3. **blocking — watchdog ownership still has two destructive races.** The launcher replaces the owner token before validating the record or checking for a live writer (`scripts/attribution_overnight.sh:14-21`). Running the real launcher with a missing record while a dummy writer and its watchdog were active caused the launcher to fail and the original watchdog to exit as superseded, leaving the writer without that guard. Separately, the watchdog checks ownership before a potentially long copy, but not again immediately before requesting a Pod stop (`scripts/attribution_watchdog.sh:37-48`). In a local mock, changing owners during the copy still caused the old watchdog to issue its stop while the replacement writer was alive. Transfer ownership only after a safe, validated takeover, and recheck/coordinate ownership through the stop operation; add tests for both races. No real Pod was touched.

4. **blocking — point 3 still does not bind the actual tokenizer to the sealed source.** `bind_sources` now checks the requested adapter, base files and test parquet, but `TransformersBackend` creates `ChatTokenizer` from the supplied directory without comparing its hashes with `sequences-v2` (`pilot_eval/attribution_backend.py:115-119`). The sequences manifest already records `inputs.tokenizer.files` (`neuron_audit_sequences.py:365-370,506-507`); `runtime()` merely logs the live identity. A different valid tokenizer or chat template can therefore be mixed with frozen prompt IDs, changing decoded text, masks, scoring and Stage D prompts while the source verification passes. Compare the actual tokenizer files with the sealed identity before generation. This is a code-inspected risk, not evidence that the planned inputs are wrong.

5. **blocking — generation can be signed off when even the reference batch OOMs.** `_generation_batches` initializes `selected=1` (`attribution_stages.py:263`) and retains it when batch 1 raises OOM (`:274-281`); qualification does not add a failing check for the missing reference (`:208-213`). A CPU mock raising OOM for every batch returned `selected: 1` despite recording batch 1 as `oom`, so automatic sign-off can accept a size that never succeeded. Require a successful reference and a tested selected size; stop before production if none qualifies. The fixes for unexercised sizes above 20 and for a later candidate OOM are otherwise present.

6. **blocking — a raw contradiction is still labelled as an after-Holm conclusion.** `primary1_adjusted` adjusts only `supported` outcomes and leaves `contradicted` unchanged regardless of Holm (`attribution_report.py:309-317`), while `render` calls all outcomes `Outcome after Holm` (`:460-463`). A fixture with raw `contradicted`, p=0.5 and Holm adjusted p=1.0 still produced the headline `contradicted`. The reported primary-1 p-value is for the support conjunction, not a separate adjusted test of contradiction. Label the contradiction explicitly as the raw interval-based classification, or implement a separately specified adjusted test; do not imply the existing Holm result establishes it.
