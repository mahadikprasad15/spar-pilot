# Experiment engineering lessons

Read this before designing or building experiment, evaluation, or remote-run workflows. During review or investigation, add or update a lesson when a serious finding could affect future work. Keep entries concise and link to evidence; distinguish a demonstrated failure from a code-inspected risk and update the status only after verification. Track specific fixes in the project issue tracker and add focused regression tests where useful. Record lasting design decisions in an ADR when the rationale needs to survive implementation changes.

## Neuron audit review, 2026-11-11

Review of commit `ed4e8d3`; findings below are review-time observations, not assertions about current fix status. Check the current code and tickets before acting on them. The 152 audit tests passed on CPU in the project environment; no real-GPU qualification or full production run was established by that review.

- **Test the real export path.** An online preflight can pass while the production worker remains offline and cannot upload. Run a small upload and fresh readback through the same online process used by the real exporter. The offline Hub failure was reproduced. Evidence: `pilot_eval/neuron_audit_production.py` (`main`, `_package_arm`) and `pilot_eval/neuron_audit_preflight.py` (`hf_online_subprocess`).
- **Exercise recovery with an empty local disk.** A resume test that keeps the original Pod's local files does not establish recovery on a new Pod. Verify all expected batches are restored or packaged from persistent storage, and that a complete export contains every expected unit. A missing restore request was reproduced; incomplete export was identified by code inspection. Evidence: `pilot_eval/neuron_audit_production.py` (`_collect_arm`, `_package_arm`) and `pilot_eval/neuron_audit_export.py` (`package_arm`, `publish_final_manifest`).
- **Verify the persistent mount, not just a writable path.** A writable directory can be on ephemeral Pod storage. Check the actual mount and intended volume identity before calling a copy durable. This was a code-inspected risk. Evidence: `pilot_eval/neuron_audit_preflight.py` (`storage_probe`, `volume_record`).
- **Bind measurements and resumed work to their actual inputs and runtime.** Verify the loaded adapter, sequences and code against the qualified records; bind reused qualification and blocks to compatible runtimes and run identities. Reject conflicting duplicate arm/example records. Silent replacement of a duplicate with a different plan identity was reproduced with a fixture; other identity gaps were code-inspected. Evidence: `pilot_eval/neuron_audit_production.py` (`check_qualification`, `_load_state`, `_collect_arm`), `pilot_eval/neuron_audit_qualify.py` (`Qualification`), and `pilot_eval/neuron_audit_selection.py` (`Discovery`).
- **Treat malformed lineage as unresolved.** A present file is not evidence that it was successfully parsed; fail or explicitly mark coverage incomplete if question text cannot be read. A malformed JSONL line causing question hashes to be discarded was reproduced. Evidence: `pilot_eval/neuron_audit_sequences.py` (`_lineage_file`, `_leakage`).
- **Enforce elapsed-time limits independently of forecasts.** Check the actual approved budget at work-unit boundaries, account for previous attempts and export time, and report whether the Pod remains billable. Missing qualification enforcement and production checks only at arm boundaries were identified by code inspection. Evidence: `pilot_eval/neuron_audit_qualify.py` (`Qualification.run`) and `pilot_eval/neuron_audit_production.py` (`Production.run`).
- **Test version checks against the target GPU build.** An exact comparison of `2.9.0` and `2.9.0+cu128` rejected the latter in a reproduction. Define and record the intended package and CUDA-build policy before deployment. Evidence: `pilot_eval/neuron_audit_preflight.py` (`check_interpreter`).
- **Keep reporting caveats and controls visible.** Label proxy numerical floors as proxies, retain per-layer references and show matched controls. A signed average across neurons can hide large opposite-direction changes; report an appropriate magnitude alongside it. These were identified by code inspection and a small numerical example. Evidence: `pilot_eval/neuron_audit_report.py` (`build`, `render`).

## Neuron audit Colab rehearsal r1, 2026-11-11

Bounded rehearsal on Colab (A100-SXM4-40GB, Python 3.13, torch 2.9.0+cu128) of 03b → 04 → 05; each failure below was demonstrated on that run and fixed with a regression test. Ticket notes: 03b, 04, 05 under `.scratch/joint-neuron-adapter-audit/issues/`.

- **Make child-process errors visible.** Colab does not display a subprocess's own stderr, so a failed step showed only an exit code. Stream the child's stdout and stderr into the notebook. Fixed in `61797dc` (notebook `sh()`).
- **Remove preinstalled packages that pin to another build.** After pinning torch 2.9.0, Colab's preinstalled torchvision no longer matched, and `transformers` imports torchvision whenever it is present, so `import peft` failed (`operator torchvision::nms does not exist`). Uninstall packages the experiment does not use before pinning. Fixed in `735ff59`.
- **Do not let test fixtures supply what the real model lacks.** Qwen2.5's `config.json` has no `pad_token_id` (the pad token is in `tokenizer_config.json`); the CPU fixture set one, so every real arm failed only on GPU. Take such values explicitly from the pinned source used in training, record them and recheck them downstream. Fixed in `c5d4f1a` (`pilot_eval/neuron_audit_collector.py`, `neuron_audit_qualify.py`, `neuron_audit_production.py`).
- **Bind resumable stages to the code that produced them.** A sealed preflight stage from an earlier commit was reused after a fix, so the summary named the wrong commit. Production stage identity now includes the code commit and every stage records it. Fixed in `2d53bb3` (`pilot_eval/neuron_audit_qualify.py`).
- **Make rehearsal subsets cover every group the later stages need.** Longest-first packing puts short GSM8K rows only in the last batches, so a first-batch rehearsal gave selection zero math rows and an opaque numpy error. Choose covering subsets and refuse clearly on empty groups. Fixed in `558e77e` (`pilot_eval/neuron_audit_production.py`, `neuron_audit_selection.py`, `neuron_audit_report.py`).
- **Apply rehearsal reading modes in every stage that reads the subset.** 05 read only rows every arm collected, but 06's held-out reader did not, so the report asked for all 97 held-out math rows (and its error wrongly said "discovery"). The report now uses the same rehearsal mode and names the split. Fixed in `cf376d8` (`pilot_eval/neuron_audit_report.py`, `neuron_audit_selection.py`).
- **Capture every child process a notebook step starts, including the last one.** The evidence upload succeeded but its receipt line went to the child's own output, which Colab hides; the receipt had to be read from the saved file. Fixed in `e8e9e46` (notebook evidence cell). Evidence for the whole rehearsal: `neuron-audit/rehearsal-evidence-r1/` at revision `17ad7108` in the private HF dataset.

## Attribution design review, 2026-11-13

- **Keep confirmation outcomes out of visible rehearsals before selection is frozen.** A rehearsal label prevents reuse of its artifacts but cannot prevent people from adapting a later plan after seeing outcomes on the same questions. Use separate calibration questions or freeze the selection and analysis first. This is a design-time risk, not a claim that leakage occurred: the draft schedules a confirmation-subset ablation report before the selection freeze. Evidence: `.scratch/adapter-neuron-attribution/spec.md` (§Selection freeze and §Run tiers), `issues/05a-colab-rehearsal.md` in that folder, and `.scratch/adapter-neuron-attribution/review-round-1.md` (point 1).
- **Size retained activations from the formula before choosing a backward design.** The draft held `down_proj` inputs for all 28 layers during backward and estimated ~4 GB; at 16k padded tokens it is 16,384 × 8,960 × 4 B × 28 ≈ 15.3 GiB before the model, graph and logits. Draft v2 stores only the per-token scalar ∂M/∂c_t and recomputes z in a forward-only pass. Design-time finding from review point 16, not an observed OOM. Evidence: `.scratch/adapter-neuron-attribution/review-round-1.md` (16) and `review-response.md`.
- **In PEFT 0.18.0 the scaled LoRA branch is not a module output.** `Linear.forward` computes `lora_B(lora_A(dropout(x))) * scaling` inline, so a hook on the wrapped linear sees base + branch, and a scaled copy built inside a hook is not in the graph. Gate the `lora_B` output instead; the scale cancels in ⟨∂M/∂out, out⟩. Code-inspected (review point 7); to be confirmed by the CPU fixture in ticket 03.
- **Give a frozen model a differentiable input when measuring activation gradients.** In a tiny Qwen2/PEFT 0.18 CPU reproduction, freezing every parameter and multiplying each branch by the constant `1.0` left logits without a gradient graph; backward failed. Marking the embedding output as requiring gradients made backward succeed while weights stayed frozen. This is a design-time risk in a possible implementation, not a failure of existing attribution code. Evidence: `.scratch/adapter-neuron-attribution/review-round-2.md` (point 23).
- **Budget the gradients returned by autograd as well as saved activations.** The proposed rank-one attribution requested every full-width branch gradient simultaneously; gate/up gradients alone would occupy about 30.6 GiB at 16k tokens. A tiny Qwen2/PEFT CPU check found the scalar-read contraction agrees with the branch-output contraction, so it can avoid that returned-gradient allocation. This is a design-time estimate, not a measured GPU peak. Evidence: `.scratch/adapter-neuron-attribution/review-round-3.md` (point 1).
- **Test the actual export scope with new file types.** In a local fixture, `neuron_audit_export.snapshot` marked standalone `run_summary.md` and `run_summary.json` unsealed and included neither. Put new outputs in a supported sealed layout or extend the export contract, then verify they appear in a clean-root restore. Evidence: `.scratch/adapter-neuron-attribution/review-round-3.md` (point 2).

## Attribution implementation (CPU), 2026-11-13

- **Leaving `disable_adapter()` unfreezes the adapter in PEFT 0.18.0.** After `with model.disable_adapter(): ...` exits, the active adapter's `lora_A`/`lora_B` weights have `requires_grad=True`, even if they were frozen before. Reproduced on the tiny Qwen2 fixture. A frozen-weight instrument that computes an untuned reference this way silently gets trainable adapters on its next pass. `attribution_instrument.frozen_disable_adapter` restores each parameter's flag, and the instrument refuses any unfrozen weight. `set_adapter` likewise marks the new adapter trainable, so re-freeze after every switch.
- **FP32 finite differences have a resolution floor.** For a metric of size |M| at ε = 1e-2, central differences resolve only about ulp(|M|)/ε ≈ 1e-5. Effects near that size cannot validate an attribution. Compare against effects well above it, and state the floor alongside any finite-difference tolerance (06b's real-model check uses ε = 1e-2 in FP32).

- **Gate resumption on the decision, not just a completed calculation.** A CPU fixture reproduced a failed qualification being marked complete and skipped on restart, allowing production without sign-off. Evidence: `.scratch/adapter-neuron-attribution/review-round-4.md` (5, 8); review-time observations; fixed in `3cf8537` and `f5dc3bb`, verified by CPU chain tests (`review-response-round-4.md`, 5 and 8).

Fixed in `50d6245` with a CPU test that fails on both patterns; the GPU path itself is not yet verified (06a).

## Attribution Colab rehearsal 06a r1, 2026-11-16

- **A restored prep snapshot is not all of a manifest's inputs.** The joint audit's `prep-v2` snapshot holds sequences, inventory, adapters and tokenizer but not the GSM8K parquet files the sequences-v2 manifest pins (path, revision and SHA-256 only). The first 06a run stopped at `bind_sources` before any GPU work. Its message said "differs" when the file was in fact absent; it now says "missing". The notebook fetches both parquets from `openai/gsm8k` at the pinned revision and refuses any whose hash differs (cell 4b). Demonstrated on Colab (A100-40GB); fix not yet verified on Colab.
- **Verify a restored record against its seal, not by rebuilding it from originals that weren't restored.** `neuron_audit_inventory.verify` re-derives the inventory from the joint audit's original source files; on Colab that failed ("current sources differ") although the sealed inventory was intact. Check the seal, and bind the inputs actually used (`bind_sources`). Also, a covering-set driver must mark steps that depend on a failed step as skipped, with the reason; in r1 one failure produced eight confusing errors and an "ok" attribution over zero rows. Demonstrated on Colab (A100-40GB); fixed with CPU tests, not yet re-run on Colab.
- **Don't recompute a gradient pass on a whole split when its results are already sealed.** In 06a r2 the rehearsal's selection re-ran attribution (forward plus two backwards) over all calibration rows in one batch and ran out of memory on a 40 GB A100; the attribution step had just sealed the same numbers row by row. Read sealed units for selections, bound every GPU batch by a qualified token budget, and free cached memory between independent steps. Demonstrated on Colab; fixed with CPU tests, not yet re-run.
- **An FP32 finite difference cannot validate effects near FP32 resolution.** In 06a r3 the qualification's FP32 central difference (ε = 0.01) disagreed with correct attributions by up to 60× on single-neuron effects (~1e-5); with an FP64 reference the same comparisons agreed within 8%, and adapter-level effects within 0.05% (`.scratch/adapter-neuron-attribution/06a-r3-fd-diagnosis.md`). Diagnose with a precision ladder (FP32 small step, FP32 larger step, FP64) before calling either side wrong; a relative tolerance stays sensitive to near-zero effects even then. Demonstrated on Colab; FP64 reference adopted by the user 2026-11-16.
- **`model.double()` is not an FP64 model for Qwen2 in transformers 4.57.** The eager attention softmax, every RMSNorm and the rotary embedding cast to FP32 internally (`modeling_qwen2.py` lines 114, 198, 296–301). An "FP64" finite-difference reference built that way still carried FP32 rounding from every block, and a correct FP32 attribution looked wrong by up to 93% on single-neuron effects. With those steps in FP64 (`attribution_instrument.full_fp64`) the same comparisons agreed within 5e-5 (06a diagnostic 4, `.scratch/adapter-neuron-attribution/06a-r3-fd-diagnosis.md`). Check a precision claim against the model code, and test it: a true FP64 finite difference is consistent across step sizes. Demonstrated on Colab A100-40GB and on the CPU fixture.

## Attribution Pod rehearsal pod-1 setup, 2026-11-16

- **Keep the Hugging Face cache off the RunPod volume: downloads through a cache on it can come back empty without error.** On the A100 Pod, `HF_HOME` defaulted to `/workspace/.cache/huggingface/`, on the sl-0 volume (`fuse.geesefs`). `hf_hub_download` of the prep-v2 archive returned a 0-byte file with no error. HF's own record (size 30,164,599, SHA-256 `705149f8…`) matched the upload receipt, and only the restore's hash check caught it. With `HF_HOME=/root/hf-home` on the container disk, the download matched both with and without xet (hf-xet 1.8.0); with the volume cache and xet disabled it was still empty. Set `HF_HOME` on the container disk before any HF call on a Pod (`pod-runbook.md` step 1), and hash every download. Confirmed on the Pod by a three-way download test.
- **Run the real preflight body before the Pod: a fake backend hid a wrong argument.** Launch 1 of the Pod rehearsal failed in preflight after 24 s with `TypeError: string indices must be integers`. `TransformersBackend.preflight` passed the work-directory path to `neuron_audit_pod.disk_problems`, which takes the dict from `local_disk(path)`. The CPU chain tests replaced the whole backend with a fake, and 06a's driver never calls preflight, so this line first ran on the Pod. A CPU test now runs the real body with only CUDA, the volume mount and the Hub stubbed (`tests/test_attribution_backend.py`). Teardown worked as designed on that failure: the volume copy and the HF export (label `rehearsal-pod-1`) were both verified, the final summary was uploaded, and the Pod was stopped. Confirmed from the HF summary; fixed with a red/green CPU test.
- **The chain's volume state is per volume, not per run: a new record needs a new run ID and the old state moved aside.** `attribution/chain/state.json`, the budget, the marker and the sealed `attribution/launch` all live at fixed paths on sl-0. A relaunch under the same run ID restores the old sealed launch directory, and `seal_run` refuses a record that differs (as one with a new code commit does). A new run ID is refused while `state.json` names the old one. After a code fix, move `$VOL/attribution` aside and launch under a new run ID. Found by code inspection after launch 1; not yet exercised on a Pod.
- **Type-check every value read from YAML before a run starts: PyYAML reads `19.5e12` as text.** YAML 1.1 (PyYAML `safe_load`) treats a float only when the exponent has a sign (`19.5e+12`). The Pod rehearsal record's `compute.fp32_peak_flops: 19.5e12` was sealed as the string `'19.5e12'`, and launch 2 failed 761 s into qualification when `attribution_gpu.mfu` compared it with 0. `seal`/`load_launch_record` checked for missing values, never for types. They now refuse text where a number belongs and any bool (`attribution_chain.mistyped`), so the same mistake stops at `seal` in a second. Launch 1 (path where a dict belonged) and launch 2 are the same class of bug: an unchecked type at a boundary reached for the first time on the Pod. Confirmed from the HF summary of `rehearsal-pod-2`; fixed with red/green CPU tests.

## Attribution review rounds 6–7, 2026-11-16

- **Make the watchdog's "my writer died" rule depend on ownership taken only after every launch check.** Round 6 made the watchdog stop the Pod as soon as its writer exits without completing (so a startup crash no longer bills for hours). Codex (round 7) showed, with the real `resume_decision` and watchdog script and mock stop commands, that the launcher still wrote its owner token before checking for a live writer: an accidental second launch would take ownership, be refused by the chain, and its watchdog would then stop the Pod under the live first run. The launcher now locks the container disk (`flock`), runs `attribution_chain precheck` (record and writer marker) and only then takes ownership; failures before that print a boxed "NO RUN STARTED … still running" with the stop command and stop nothing. Fixed in `710d2af`; verified by `tests/test_attribution_launcher.py` against the real scripts on CPU, not yet on a Pod.
- **Test the real backend boundary on CPU with inputs built the way the Pod's are; it catches what fakes cannot.** `tests/test_attribution_realpath.py` runs `Chain` → `Stages` → the real `TransformersBackend` on a sealed, real-format world (`save_pretrained` Qwen2 and PEFT arms, a `tokenizers` tokenizer with a chat template, inventory-v2, sequences-v2 from the real `prepare`, the launch record sealed from the actual rehearsal YAML), stubbing only CUDA memory counters, the volume mount, the Hub and the stop command. Putting back each Pod failure made it fail with the Pod's exact error (`string indices must be integers`; `'<=' not supported between 'str' and 'int'`). To make the real base-correct filter accept rows, the base model's `o_proj`/`down_proj` are zero, so it is an exact bigram model wired to answer `Step\n#### 7`. Fixture numerics matter: saturated logits (±360) or large adapters made the FP32 instrument fail its own finite-difference and batch-invariance checks, which is the checks working, not a pipeline fault. Watch on the Pod: batch invariance is relative to the largest attribution, so when attributions are small next to the metric's FP32 resolution it can fail on rounding alone (fixture: 1.6e-6 absolute, 1.03e-4 relative). Verified on CPU only; added 2026-11-16 in `0f6d46c`.

## Correctness-attribution review, 2026-11-18

- **Check whole-group feasibility before declaring a matched control unavailable.** The existing `attribution_ablation.matched_controls` chooses controls sequentially; an early random choice can consume the only eligible control for a later target even when a complete assignment exists. Confirmed by executing the actual function from commit `1c572596f742677f2cebf4f15907464fa94ac5b9` on a two-target synthetic fixture; this is not evidence that prior real-study controls were affected. Use a seeded group-wise feasibility/matching algorithm and regression-test the counterexample without loosening the match criteria. Tracked in `.scratch/c-attribution-pilot/issues/06-interventions-selection-freeze.md`; details and the fixture are in `.scratch/c-attribution-pilot/review-round-1.md`. Fix not yet implemented or verified.

- **Adapt watchdog semantics when a new run has no time cap.** The existing `scripts/attribution_watchdog.sh` requires an absolute deadline and terminates a live writer when it passes. The C-attribution design explicitly removes elapsed-time caps, so reusing that script unchanged would contradict the design; a disabled-deadline mode must still handle a writer crash and preserve ownership. Record last progress separately: a live but stalled process is not evidence of progress. This is a code-inspected compatibility risk for an unimplemented runner, not an observed failure of the new pilot. Tracked in `.scratch/c-attribution-pilot/issues/09-runner-launch-record.md`.

- **Separate a verified response file from a verified sampling policy.** The online and offline GRPO response catalog entries had `evidence.status: verified` and an `on-policy` label even though the resolved logits processors had not been verified and the repetition settings relied on unhashed generation code. The file and checkpoint checks remain useful, but they cannot establish the exact sampling distribution. The entries now mark that policy evidence as inferred and the label as provisional; ticket 05 retains the processor check. Confirmed by comparing the catalog entries with `.scratch/c-attribution-pilot/spec.md` (source-run evidence); this does not establish that the actual policies differed.

- **Specify the producer of each target mask at a pipeline boundary.** The C-attribution metric consumes `masks.seq_targets` as token positions, while ticket 02 initially specified concatenating the prompt and generated tokens without explicitly constructing that mask. The spec already required every generated token, including EOS or the last capped token; ticket 02 now names the exact range and tests it. This is a specification handoff gap found before the row builder was implemented, not a demonstrated error in a finished run. Evidence: `.scratch/c-attribution-pilot/issues/02-behaviour-rows.md`.

- **Check qualification coverage requirements against per-arm data counts.** The C-attribution spec required 16 real rows per arm to include a capped response, while its own source inventory records zero capped online-GRPO rows. Implemented literally, that requirement could not be met and would block the run. The spec and tickets 05/11 now require a capped row where present, record the online absence, and cover a capped sequence in a CPU fixture. This is a confirmed design contradiction found before implementation, not an observed GPU-run failure. Also distinguish reconstructed cached decoding from original generation scores that were never saved. Evidence: `.scratch/c-attribution-pilot/spec.md` (Data and provenance; GPU qualification).
